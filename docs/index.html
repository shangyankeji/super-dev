产品定位

Super Dev 负责规范宿主里的 AI 开发过程。

宿主负责模型推理、联网检索、终端调用和真实编码。Super Dev 负责 research、三文档、确认门、Spec、前端验证、质量门禁和交付标准，把整个开发过程拉回同一条流水线。

宿主负责执行

模型、工具、联网、改代码、运行项目，这些都由宿主完成。

Super Dev 负责治理

强制 research、三文档、确认门、前端运行验证、质量门禁和交付标准。

项目产物可审计

research、PRD、Architecture、UI/UX、Spec、运行验证、交付报告都会落到文件。

安装方式

安装方式

先把工具装好，再进入宿主接入引导。安装阶段只需要弄清三件事：会安装什么、不会安装什么、下一步怎么触发宿主开始工作。

安装说明

  • pip 或 uv 会自动安装 Super Dev 的 Python 依赖。
  • 不会自动安装 Claude Code、Cursor、Trae、Gemini CLI、VS Code Copilot 等宿主本体。
  • 终端输入 super-dev 后，会进入宿主安装引导，并把 20 个统一接入宿主的对应协议面写入宿主和项目；OpenClaw 仍是单独的手动插件宿主。
安装流程
pip install -U super-dev
# 或
uv tool install super-dev

# 打开安装引导
super-dev

# OpenClaw 用户额外安装
openclaw plugins install @super-dev/openclaw-plugin
# 或安装 ClawHub Skill
clawhub install super-dev

# 更新到最新版
super-dev update

流水线

流水线

入口命令很短，真正重要的是后面的阶段纪律。宿主接到需求后会按研究、文档、确认、实现、验证和交付推进。

01

同类产品研究

先使用宿主联网能力研究同类产品、交互模式、差异化机会和商业信号。

02

需求增强

把边界条件、异常路径、验收口径和优先级补足，避免模糊需求直接进编码。

03

三份核心文档

生成 PRD、Architecture、UI/UX 三文档，形成可审计的执行基线。

04

用户确认门

三文档完成后强制暂停，用户确认前不得创建 Spec 或继续编码。

05

Spec / Tasks

确认通过后生成变更提案与任务清单，收紧范围和顺序。

06

前端优先

先做前端、先跑起来、先可审查，再进入后端和联调。

07

后端与联调

完成 API、服务、数据层和真实交互闭环。

08

质量门禁

执行 UI Review、红队、安全、性能和架构阈值检查。

09

交付与发布演练

交付包 ready、演练 passed、release readiness 通过后才算完成。

流程控制

流程控制

如果项目已经进入中后段，不需要从头再跑。你可以查看当前状态，回到某个阶段，直接跳到某个阶段，或者手动确认关键门后继续推进。

回到三文档阶段

用户补需求、业务范围变化、或者需要重做方案时，直接回到 docs 阶段更新三文档，再继续后续流程。

控制
super-dev run prd
super-dev run architecture
super-dev run uiux
# 或直接回到三文档阶段
super-dev jump docs

回到前端 / 后端 / 质量阶段

UI 重做、接口调整、交付前复检，都可以从对应阶段重新顺序推进，不必从 research 再跑一遍。

控制
super-dev run frontend
super-dev run backend
super-dev run quality

跳转与确认

如果你已经明确目标阶段，可以直接 jump；如果只是要清掉某个关键门，则使用 confirm。

控制
super-dev status
super-dev jump quality
super-dev confirm docs --comment "三文档已确认"
super-dev confirm preview --comment "前端预览已确认"
super-dev run --resume

知识与门禁

知识库与门禁

本地知识库、确认门、运行验证和交付标准决定了这条流水线如何执行。

知识库优先

当 knowledge/ 和 knowledge-bundle 存在时，宿主必须先读本地知识，再做外部研究。

  • research 前置知识读取
  • PRD / Architecture / UI/UX 阶段化映射
  • quality / delivery 继续复用基线

改动前先看影响范围

接手旧仓库、修改登录流、重构 API 或动关键状态流前，先跑 repo-map、feature-checklist 和 impact，把范围覆盖率、受影响模块和回归重点确认清楚。

  • super-dev repo-map
  • super-dev feature-checklist
  • super-dev impact "变更描述" --files ...

代码库理解与回归守卫

复杂仓库不要靠宿主临场猜结构。先生成依赖图，再把影响分析转换成可执行的回归清单。

  • super-dev dependency-graph
  • super-dev regression-guard "变更描述" --files ...
  • 先补回归重点再修改关键路径

前端运行验证门

必须有 frontend-runtime 报告通过，中后段才允许继续。

  • preview.html
  • frontend-runtime.json
  • 运行通过后再进后端

质量与交付门

UI Review、Spec Quality、交付包、发布演练和 release readiness 共同定义“是否可交付”。

  • UI Review
  • Spec Quality
  • Proof Pack / release readiness

排障

排障

大多数问题都出在宿主没有真正读取接入面。排障时优先确认 commands、rules、AGENTS、steering 或 skills 是否已被宿主加载。

排查顺序

  1. 1执行 super-dev doctor --host <host> --repair --force。
  2. 2确认安装引导输出的项目级与用户级接入面真实存在。
  3. 3完全关闭宿主，重新打开项目，并新建一个会话。
  4. 4先用 smoke 触发语句。
  5. 5如果宿主直接开始开发，优先判断当前会话没有重新加载规则。

Smoke 验收

Smoke

/super-dev "请先不要开始编码，只回复 SMOKE_OK，并说明你会先做 research、再写三文档并等待确认。"

# 非 slash 宿主
